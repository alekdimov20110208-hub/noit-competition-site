# SQL migrations

P1A created the migration runner and `public.schema_migrations` metadata boundary.
The current set contains the original two reviewed P1B migrations and the P2C addition.

P2C adds immutable `0003_event_invitations.sql`: Event invitations with only hashed
bearer tokens, finite expiry/state timestamps, scoped Event/User membership FKs,
unique hashes, pending Event/email indexing and RLS without browser policies. Applied
0001/0002 remain unchanged. Run the migration CLI explicitly, then run it again to
verify the already-applied result. No migration resets or drops development data.

| File                         | Source and scope                                                                                                                                                                                               |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0001_better_auth_core.sql`  | Exact auth SQL generated by official `auth@1.7.7` from locally installed `better-auth@1.7.7` runtime configuration; User/Session/Account/Verification and configured `user.active`.                            |
| `0002_budograph_core.sql`    | BudoGraph Event/EventMember/Task/ActivityEntry schema, scoped constraints/indexes, timezone validation, a narrow append-only history guard, and RLS without public policies on the eight auth/business tables. |
| `0003_event_invitations.sql` | P2C Event invitations, hash-only tokens, expiry/acceptance/revocation constraints and scoped accepted membership; RLS without browser policies.                                                                |

Run `pnpm db:migrate` from the repository root after configuring the untracked
`server/.env` using `server/.env.example`. The source and compiled CLI both read
this directory; the build does not copy SQL into its output.

Migrations use names such as `0001_description.sql`, with four digits
from `0001` through `9999` and lowercase snake_case descriptions. Regular UTF-8
SQL files only; invalid SQL filenames, symlinks and duplicate versions fail the
run. Non-SQL files such as this README are ignored. Versions sort numerically
because all versions have four digits; new versions must follow applied history.

The runner uses one checked-out PostgreSQL client and holds a fixed session
advisory lock across history validation and all migrations. Concurrent runners
wait for this same lock. It records version, full filename, SHA-256 checksum of
the exact file bytes and a database-generated `applied_at` timestamp. Every
previously applied file must still exist with the same filename and checksum
before any pending migration starts. Editing even whitespace or line endings
changes the checksum. Fix schema changes with a new migration; do not edit or
delete applied files or reset metadata to bypass validation.
Keep SQL files with LF line endings, including on Windows; the repository's
`.gitattributes` enforces LF for these files so deployment checkouts retain the
same checksum.

Each file and its parameterized metadata insert run in a separate transaction.
A failure rolls back that file and stops the run; earlier committed migrations
remain applied. SQL must support a PostgreSQL transaction. Migration files are
reviewed repository code: do not include `BEGIN`, `COMMIT`, `ROLLBACK`, advisory
lock changes or writes to `schema_migrations`. Operations such as `CREATE INDEX
CONCURRENTLY` are not supported by this transaction runner. There are no
automatic down migrations or SQL parsing/rewrite features. Destructive database
changes require separate user approval before execution.

## Better Auth generation provenance

Current official Better Auth documentation was consulted for the installed
**1.7.7** release, including [PostgreSQL integration](https://better-auth.com/docs/adapters/postgresql)
and [schema generation](https://better-auth.com/docs/concepts/cli).
The exact-version `auth@1.7.7` official CLI generated PostgreSQL SQL from a config
that imported the locally installed runtime `createAuth` with the existing `pg`
Pool. The initial generation command was:

```sh
pnpm dlx auth@1.7.7 generate --config tmp/auth-generation.ts --output tmp/better-auth-1.7.7.sql --yes
```

Generated SQL SHA-256 before adding migration provenance comments:
`1ff812a96bd306d7124d1d5a3e74b20d7ae5c04e2948bab0d8614e768641d670`.
The statements were preserved without manual auth-table recreation or type
rewrites; the tool natively emitted TIMESTAMPTZ. The migration includes the
configured `active` additional field. `defaultValue: true` is applied by Better
Auth; the generated User column has no database DEFAULT and raw fixture inserts
must explicitly provide it. Auth-specific cascades/types follow the generator.
The runner's applied-file checksum includes provenance comments and is distinct
from the raw generated-output digest.

The checked-in reproduction config is `server/scripts/auth-schema-config.ts`;
the guarded wrapper is `server/scripts/generate-auth-schema.ts`. From the root:

```sh
pnpm server:auth-schema
```

It runs the pinned official CLI with a new ignored output path for each
invocation, `tmp/better-auth-1.7.7-<random-uuid>.sql`, and checks that a reported
generated file is nonempty. It prints that review path only after verifying the
file. An up-to-date schema with no SQL output is reported explicitly, without
mistaking an earlier output for a new generation. It suppresses potentially
sensitive generator diagnostics and loads local values without printing
credentials. Kysely-backed generation introspects the configured
database: use an approved empty/disposable database when reproducing a complete
initial schema; an already-migrated database may emit no pending SQL. Never
overwrite an applied migration with later generator output. Temporary generator
config/output are not committed. No `auth migrate` or unmanaged runtime migration
is used; reviewed persistent changes always use this repository runner.

## Schema and access guardrails

Business UUIDs are generated by trusted server `crypto.randomUUID()` without
extensions. Event start/end and task deadline are finite DATE calendar values;
audit/auth/activity timestamps are real TIMESTAMPTZ instants. Event timezone
validation uses PostgreSQL's installed timezone catalog, excluding POSIX/right
and localtime/posixrules names. Use IANA identifiers such as `Europe/Sofia` or
`UTC`. Title/name/role/version/date checks, same-Event membership composite FKs,
acceptance pairing/current-assignee checks, and actor User/member consistency are
stored constraints. Business FKs restrict deletion to preserve history.

One statement trigger rejects ActivityEntry UPDATE, DELETE, and TRUNCATE with
SQLSTATE `55000`. This is a narrow immutability guard, not event sourcing or
automatic business commands. Future services still need owner/active-organizer
consistency, active-assignee/deactivation safeguards, scoped target validation,
atomic version checks, and business/history transactions.

RLS is enabled with no public policies for direct Supabase API denial. The trusted
backend connection requires owner/bypass capability with separately reviewed
privileges. RLS does not replace authenticated Event-scoped server authorization;
dedicated least-privilege deployment grants remain a documented limitation.

## Verification boundary

The migration runner's offline tests use temporary files and explicit protocol
doubles; discovery, checksums, history validation, failure rollback, locking and
cleanup results are not PostgreSQL-engine evidence.

`pnpm server:test:integration` requires `RUN_DATABASE_INTEGRATION=1`, refuses
production mode, and requires migrations already applied by the explicit CLI.
It checks actual schema/history/checksums and exercises constraints in disposable
fixture transactions, using savepoints and final rollback without resetting or
dropping tables. Separate real auth verification creates/logs out only its own
sessions; it does not import demo business data. Exact executed results are in
[test evidence](../../docs/TEST_EVIDENCE.md).
