# BudoGraph P2C: Event invitations and invite-only onboarding

P2C extends the approved P1/P2A/P2B product with Event-scoped invitations. An
active Organizer invites an email from Team; a matching existing account signs
in, or a new account registers through that valid invitation. The recipient must
explicitly join. The resulting active EventMember has `accessRole: MEMBER` and
an empty operational role. Assignment still requires separate explicit acceptance.

The user's P2C implementation request authorizes this stage. The approved core
idea, architecture, responsibility semantics and locked Dashboard/Tasks/Team
composition are retained. P3 is not started. Automated verification is recorded
in `TEST_EVIDENCE.md`; human P2C acceptance is not invented.

## Schema and secure delivery

Immutable migration `0003_event_invitations.sql` adds `event_invitation`, with
Event and User references, normalized invited email, inviter, unique SHA-256
digest, server timestamps, expiry, acceptance and revocation. Acceptance has a
paired timestamp/User and same-Event membership FK; acceptance and revocation
cannot coexist. RLS is enabled without direct browser policies. Pending lookup
is indexed by Event/email/expiry. Older migrations remain unchanged.

Each bearer token is generated by Node `randomBytes(32)` (256 bits), encoded as
43 base64url characters, and hashed with SHA-256. Only the digest is persisted.
Tokens expire seven days after creation according to the database clock.
Membership uniqueness remains enforced by `(event_id, user_id)`. Event row locks
serialize duplicate invitation checks and the create/revoke/accept commands;
the time-dependent pending rule is not expressed as a misleading unique index.

No outbound email provider was configured, and none was added. The creation
response contains a relative development invite path for the current origin.
The authorized Organizer dialog shows a clearly labelled copyable link once in
memory, with selectable manual-copy fallback. It does not claim email delivery.
Closing/switching/logging out discards that link; hashes cannot recover it.
Revoke and recreate a still-pending invitation when its link is lost.

## API contract

| Command                                                      | Body                    | Authority / response                                                                            |
| ------------------------------------------------------------ | ----------------------- | ----------------------------------------------------------------------------------------------- |
| POST `/api/events/:eventId/invitations`                      | `email` only            | Active current-Event Organizer; 201 safe invitation plus development path                       |
| GET `/api/events/:eventId/invitations`                       | None                    | Active current-Event Organizer; pending/expired records, no tokens/hashes                       |
| POST `/api/events/:eventId/invitations/:invitationId/revoke` | Empty                   | Same-Event Organizer; pending-only, repeated revocation is safe                                 |
| GET `/api/invitations/:token`                                | None                    | Bearer holder; pending Event name/email/expiry, terminal state only                             |
| POST `/api/invitations/:token/register`                      | `name`, `password` only | Signed-out bearer holder; valid pending invitation fixes email; generic sign-in-required result |
| POST `/api/invitations/:token/accept`                        | Empty                   | Active authenticated matching canonical stored email; canonical Event ID/result                 |

Writes require a trusted Origin and reject cross-site Fetch Metadata. Bodies are
strictly whitelisted; callers cannot choose actor, Event, User, role, token,
expiry, timestamps, acceptance or membership. Route IDs are never authority.
Queries are parameterized. Creation rejects active/inactive existing members
and valid pending duplicates. Archived Event writes and inactive actors fail
closed. No inactive member is reactivated.

Public lookup is intentionally minimal: possession of a valid invitation allows
its intended email and Event name to be displayed, but never roster, tasks,
private Event identifiers, inviter identity or authentication internals. Terminal
lookup responses contain only state. Invalid tokens use a non-enumerating 404.
Registration responses do not provide an account-existence endpoint.

The bounded single-process limiter permits 120 invitation requests/minute/IP
and five registration requests/minute/IP, caps its map at 10,000 entries and
removes expired entries. A shared limiter is required before multiple instances.
Responses use `no-store` and `no-referrer`; the HTML referrer policy protects
navigation to login. Backend log serializers whitelist method/status only and
omit paths, query, bodies, headers and raw exceptions. Better Auth diagnostics
are disabled; Vite proxy diagnostics redact invitation bearer path segments.
Production proxy/access logs require the same review before deployment.

## Better Auth and transaction boundary

Library reference: [Better Auth server API](https://better-auth.com/docs/concepts/api)
and [email/password authentication](https://better-auth.com/docs/authentication/email-password).
The installed 1.7.7 source and real browser verification are authoritative for this
repository's behavior.

The default HTTP Better Auth instance keeps `disableSignUp: true` and disables
`/sign-up/email`. A separate private server-only instance uses the same library,
database, schema, secret and password/session configuration to call
`registration.api.signUpEmail`. Its handler is never exposed through HTTP.
The invitation service validates/locks the invitation before that call, fixes
email from the invitation and forwards only name/password. No password hashing
or account/session system is reimplemented. Normal sign-in establishes the
ordinary database-backed session; account creation does not automatically join.

Better Auth owns a separate account transaction. If account creation succeeds
but joining later fails, the account can remain and sign in to retry a still-valid
invitation. Registration never consumes the invitation or creates an EventMember.
This is not a single account-plus-membership database transaction.

Acceptance locks the Event and invitation, rechecks active User and canonical
email, validates pending/unexpired/unrevoked state, archived state and membership,
then creates only a MEMBER, consumes the invitation and writes one append-only
`invitation.accepted` ActivityEntry in one business transaction. Consumption checks
expiry again at the final update; late expiry rolls the new membership back.
Activity failure likewise rolls membership and consumption back. Repeated acceptance
by the same still-authorized recipient returns `already_accepted` without extra
membership or history. Wrong accounts, inactive membership and forged role/User
inputs cannot join. Independently existing active membership is preserved without
promoting or overwriting its role.

## UI and existing product integration

Team adds one Organizer-only Invite member action and a restrained native dialog
with labelled email, pending/expired state, expiry and revoke controls. It preserves
the existing roster/detail layout. Modal Tab/Shift+Tab wrapping, Escape dismissal,
trigger restoration, alerts and 44px controls support keyboard use. Remote service
and cancelable transient controller handle requests and clear stale scope/identity.

`/invite/:token` is a public invitation screen within the existing auth boundary.
It provides localized context, ordinary sign-in, invite-only account creation and
explicit Join Event. The email is read-only. Wrong-account UI offers sign-out;
invalid/expired/revoked/unavailable links have safe terminal/error states. The login
return allowlist accepts only an exact internal invitation path and rejects external,
encoded-slash, query/hash or malformed destinations.

After joining, existing Event navigation refetches authoritative accessible Events
and Team members. The new Member is visible to Organizer task assignment, and new
assignment remains unaccepted until that Member explicitly accepts. A person can
be MEMBER in Event A and ORGANIZER in a separately created Event B; authority never
becomes global. Existing task versions, status, reassignment, withdrawal and explicit
reacceptance remain unchanged.

## Verification and evidence boundary

Run frontend format/check, lint, typecheck, tests and build; backend typecheck,
offline tests and build; then the enabled PostgreSQL integration suite. Integration
files run sequentially because failure fixtures temporarily add constraints with
table locks inside outer rollback transactions. Do not run live browser writes
concurrently with these constraint fixtures. No existing test is removed or skipped
to conceal failure. Migration apply and second-run idempotency use the real development
database without a reset.

`pnpm.cmd test:browser:invitations` runs real browser/PostgreSQL onboarding, membership,
assignment, race and negative flows. As with the other browser verifiers, an externally
available Playwright runtime can be supplied via `BUDOGRAPH_PLAYWRIGHT_MODULE` and
browser executable via `BUDOGRAPH_BROWSER_EXECUTABLE`; no project dependency was
added for verification. Credentials come only from ignored local environment files.
Tokens/passwords/sessions stay in memory; no HAR, cookie jar or auth dump is saved.
The ignored evidence directory holds safe aggregate reports and screenshots.

Browser-created disposable Events/tasks/accounts are intentionally retained with
their history. PostgreSQL integration fixtures roll back. Viewport emulation and
agent review do not establish physical-device, Safari/Firefox, human usability,
formal accessibility/security certification or production deployment readiness.
